# bnbloc CLI

`bnbloc` (`go build -o bnbloc ./cmd/bnbloc`) is the super-admin operator CLI:
sign in through the gateway's SSO, publish component packages, and publish
desktop app updates. It talks only to the gateway's public HTTP API.

## Sign in

```sh
bnbloc login --gateway https://bnbloc.example.com
bnbloc whoami          # gateway, subject, tenant, role
bnbloc logout          # revoke + forget the stored sign-in (the gateway is kept as default)
```

`login` reads `GET /v1/auth/sso-config`, opens the advertised SSO start path in
the browser (`open` on macOS, `xdg-open` on Linux; otherwise it prints the
URL) with `redirect_uri=<gateway>/sso-callback?cli_nonce=<nonce>`, and polls
`POST /v1/auth/sso/claim {"nonce"}` every 2 s for up to 5 minutes. The nonce is
256 random bits generated by the CLI; the gateway parks the verified identity
in its shared store under a hash of the nonce for 2 minutes (any gateway
replica can answer the claim), mints the session when it is claimed — once —
and the browser lands on a "signed in to the bnbloc CLI" page carrying no
token or code.

`logout` revokes the sign-in on the gateway (`POST /v1/auth/logout`,
best-effort: an unreachable gateway only prints a warning) and then deletes the
stored refresh token.

Only the refresh token is stored, in `~/.bnbloc/config.json` (mode 0600):
`{"gateway", "refreshToken", "subject"}`; other keys in the file are kept.

Credentials for every command, highest first:

1. `--token <session>` or `BNBLOC_TOKEN` (static bearer);
2. `BNBLOC_API_TOKEN`, a super-admin-issued API token (below): exchanged once
   per command via `POST /v1/auth/api-token` for a 1-hour session — the
   credential of unattended runs (CI); nothing is written to disk;
3. the stored sign-in: exchanged once per command via `POST /v1/auth/refresh`
   (sessions live 1 h, refresh tokens 30 days); the rotated refresh token is
   written back atomically. A refused refresh asks you to run `bnbloc login`.

The endpoint is `--gateway`, else `BNBLOC_GATEWAY`, else the stored sign-in's
gateway (default `http://localhost:7090`). A stored refresh token is only ever
sent to the gateway that issued it.

## Deployment version

```sh
bnbloc version --gateway https://bnbloc.example.com
```

Prints the CLI's own commit, then every reachable instance of every service
(`GET /v1/platform/versions`, platform super-admin): the gateway reports
itself and its embedded web bundle and samples each backend's `/version`
five times on fresh connections, so replicas behind one Service name show up
as separate instances; the CLI calls the route five times and merges the
answers, which also covers gateway replicas. Instances, commits and build
times print as a table; any skew (short and full hashes of one commit
match), unknown commit (an image built without `CI_COMMIT_SHA`) or
unreachable service prints a `SKEW …` line and exits non-zero.

## Post-deploy smoke

```sh
bnbloc smoke --gateway https://bnbloc.example.com                 # message path only
bnbloc smoke --agent codex --timeout 180s                         # also wait for your agent's reply
bnbloc smoke --keep                                               # leave the room for inspection
```

`smoke` checks the room message path of a running deployment the way the
client uses it, with the usual credential (`--token`/`BNBLOC_TOKEN`, else
`BNBLOC_API_TOKEN`, else the stored sign-in). One line per step, `PASS <step> (<ms>)[: detail]`,
`FAIL <step>: <reason>` or `SKIP …`; any FAIL exits non-zero and stops the
chain (later steps depend on earlier ones).

| Step | What it does |
|---|---|
| `auth` | resolves the session subject (refresh of the stored sign-in, or the subject of the static token) and reads `GET /v1/users/{subject}/rooms` |
| `versions` | `GET /v1/platform/versions` (sampled like `bnbloc version`): every service instance and the web bundle on one commit. Skew or an unreachable service is a FAIL that does not stop the chain (the run still fails at the end); a caller that is not a platform super-admin gets `WARN versions: not checked …` instead |
| `create room` | `POST /v1/rooms` — a private room `smoke-<utc yyyymmdd-hhmmss>-<4 hex>` |
| `open stream` | `GET /v1/rooms/{id}/events?allChannels=1&presence=0`, opened **before** sending and kept open (a non-presence observer, like the bridge) |
| `chat echo` | `POST /v1/rooms/{id}/chat` with a fresh `clientMsgId`; the `chat_message` carrying that id (and the returned sequence) must arrive on the open stream |
| `history` | `GET /v1/rooms/{id}/history` must contain the message |
| `agent reply` | only with `--agent`: a chat addressed to the agent (`recipient {ownerId, provider, core}`, the composer's shape); an assistant `agent_messages` from that owner/provider must arrive on the stream within `--timeout` (default 120s). A job-failure notice fails the step. Without `--agent`: `SKIP agent reply (pass --agent)` |
| `delete room` | `DELETE /v1/rooms/{id}` (owner delete) — runs on every path, including a failed step or Ctrl-C; `--keep` skips it |

`--agent` is matched against your own agents (`GET /v1/my/agents`) by target
id (`acme/local:codex`), `core/provider` or bare provider; the agent must be
online (its bridge connected — the bridge picks the new room up within its
~10 s room reconcile). Anything else is read as `owner/provider` or
`owner/core/provider`; another member's agent only answers when its owner's
bridge serves the room and a borrow grant exists, which a throwaway room does
not have, so use your own agent.

### Alert on failure

```sh
bnbloc smoke --alert-on-failure                         # alert every platform super-admin
bnbloc smoke --alert-on-failure --alert-to ops@corp.example,root@corp.example
```

When the run fails (any FAIL, or an error before the first step),
`--alert-on-failure` sends one admin alert (`bnbloc alert`, below) titled
`bnbloc smoke failed on <gateway>`, with every `FAIL <step>: <reason>` line
(and `--agent`) as its text and the gateway as its link, then prints
`ALERT <id> queued for … via <notifiers>`. It runs after the room cleanup.
If the alert cannot be sent (not a super-admin, no notifier reaches the
recipients, gateway unreachable) the reason is printed on stderr as
`smoke alert NOT sent: …`; the command exits non-zero either way. The nightly
workflow uses this ([ci.md](./ci.md#nightly-smoke)), and so does the
scheduled in-deployment smoke (Helm CronJob / compose `smoke` service, from
the CLI image `SERVICE=cli`; see
[production-deployment.md](./production-deployment.md#nightly-smoke)).

## Admin alerts

```sh
bnbloc alert --title "Backup failed" --text "pg_dump exited 1" --url https://ops.example/run/42
bnbloc alert --title "Maintenance at 18:00 UTC" --to alice@corp.example,bob@corp.example
```

`POST /v1/platform/alerts` (super-admin): an `admin_alert` notification
delivered through the installed notifier components to `--to` (default every
`BNBLOC_SUPER_ADMINS` entry). Title ≤ 200 characters, text ≤ 500, `--url`
an absolute http(s) URL. The gateway answers once the alert is queued
(delivery is asynchronous, with the outbox's retries); the CLI prints the
event id, recipients and notifiers. No notifier reaching the recipients is a
409. See [notifications.md](./notifications.md#admin-alerts).

## API tokens

```sh
bnbloc api-tokens create --label nightly-smoke [--subject svc:smoke] [--ttl-days 90] [--tenant <id>]
bnbloc api-tokens list
bnbloc api-tokens revoke <id>
```

A long-lived credential for an unattended caller (super-admin only):
`create` prints the token **once** (`bnbloc_at_<id>_<secret>`; the gateway
stores only a SHA-256 of the secret) — use it as `BNBLOC_API_TOKEN`. The
subject is yourself (default) or a service subject `svc:<name>` (lowercase
letters, digits, `.`, `_`, `-`); a token can never act as another person.
Each exchange (`POST /v1/auth/api-token {"token"}`, rate-limited per client
IP like login) mints a 1-hour session and re-resolves the subject's tenant
(`--tenant`, default the issuer's session tenant) and role, so a service
subject is a super-admin only while listed in `BNBLOC_SUPER_ADMINS`.
`revoke` stops further exchanges (a session already minted lives out its
hour). `list` shows every token with its state, expiry and last use, never
the secret. Issue, revoke and every exchange (allowed or refused) are
recorded in the extension audit trail (kind `api-token`, name = token id).

| Route | Who | |
|---|---|---|
| `POST /v1/platform/api-tokens` `{label, subject?, ttlDays?, tenantId?}` | super-admin | 201 with `token` (once) |
| `GET /v1/platform/api-tokens` | super-admin | `{tokens: [{id, subject, label, tenant, createdBy, createdAtMs, expiresAtMs, lastUsedAtMs, revokedAtMs, revokedBy, active}]}` |
| `DELETE /v1/platform/api-tokens/{id}` | super-admin | 204; 404 when unknown or already revoked |
| `POST /v1/auth/api-token` `{token}` | the token | `{sessionToken, subject, tenant, role, rooms, expiresAtMs}`; 401 invalid/expired/revoked |

## Search reindex and status

```sh
bnbloc search reindex                     # walk the whole room feed until done
bnbloc search reindex --cursor 'room-42/1834'   # resume an interrupted run
bnbloc search status                      # backend, readiness, index health, update queue
```

`reindex` brings the message search index up to date with the room feed.
Super-admin only: `POST /v1/platform/search/reindex` `{cursor?, maxBatches?}`
→ `{backend, scanned, updated, cursor, done}`, served by realtime. Each call
walks at most `--batches` batches of 500 rows in primary-key order (default
10, at most 50) and at most ~10 s, so it stays inside proxy timeouts; the CLI
loops on the returned cursor, printing the backend and one progress line per
call, until `done`. What a batch does depends on the backend:

- **mysql** (the default): fills `room_messages.search_text` for rows stored
  before search existed (or any row left without it). The text is the same
  the append path indexes (chat text, or the joined texts of an agent reply),
  and a row is only written while its search text is still empty, so a
  concurrent edit is never overwritten. `updated` = rows filled.
- **opensearch**: writes every row's current document (a soft-deleted message
  keeps a `deleted` document without text; a row without text has none). Run
  it after configuring a new index (backfill), after a mapping version bump
  (a new index name), or when `bnbloc search status` or the
  `bnbloc_search_index_updates_total{result="error"|"dropped"}` metric shows
  updates that never reached the index. `updated` = documents written.

Both are idempotent and safe to run while serving. A failed call prints the
cursor to resume from. The session minted from `BNBLOC_API_TOKEN` or the
stored sign-in lasts an hour; a longer run fails with a 401 and resumes with
`--cursor`.

`status` prints `GET /v1/platform/search/status` (super-admin, served by
realtime): `{backend, index?, ready, health?, documents?, error?, updates?}`.
`updates` is the answering realtime replica's queue since it started
(`queued`, `applied`, `failed`, `dropped`); with several replicas each keeps
its own. It exits non-zero when the backend is not ready.

## Organization sync

```sh
bnbloc org-sync rules                         # print the mapping rules
bnbloc org-sync set-rules --file rules.json   # replace them ({"rules":[...]} or a bare list)
bnbloc org-sync preview --email ann@corp.example --group engineering --department research
bnbloc org-sync deprovision ann@corp.example bob@corp.example
bnbloc org-sync deprovision --file departed.txt   # one id per line, - for stdin
bnbloc org-sync resync                        # re-apply the rules to every recorded member
```

Super-admin only, over `/v1/platform/org-sync/*`. Deprovisioning is the call
a directory feed makes when people leave (run it with an API token); see
[organization-sync.md](./organization-sync.md).

## Publisher keys

```sh
bnbloc keys gen --out ~/.bnbloc/component-publisher   # .key is written 0600; never overwritten without --force
bnbloc keys add --pubkey ~/.bnbloc/component-publisher.pub --label ops
bnbloc keys list
bnbloc keys rm <keyId>
```

Every signing command uses `~/.bnbloc/component-publisher.key` when `--seckey`
is not given and that file exists. `--unsigned` publishes without a signature
(dev gateways with `BNBLOC_EXT_ALLOW_UNSIGNED` only).

## Browser push keys

```sh
bnbloc keys gen-vapid   # prints BNBLOC_WEB_PUSH_VAPID_PUBLIC_KEY=… and …_PRIVATE_KEY=…
```

Generates the deployment's VAPID key pair for browser push notifications
(offline; nothing is written to disk). Set both lines on bnbloc-realtime, plus
`BNBLOC_WEB_PUSH_VAPID_SUBJECT=mailto:<ops address>` unless `BNBLOC_PUBLIC_URL`
is https; keep the private key in the deployment's secret store. See
[notifications.md](./notifications.md#browser-push).

## Publish a component

A desktop-supervised sidecar core (binaries are uploaded to the gateway's
content-addressed artifact store first; the signed package pins their sha256):

```sh
bnbloc cores publish-sidecar --name acme --version 1.4.0 --publisher acme-inc \
  --local-url http://127.0.0.1:7099 --listen-env ACME_LISTEN --supervised-env ACME_SUPERVISED \
  --binary darwin-arm64=dist/acme-darwin-arm64 --binary darwin-amd64=dist/acme-darwin-amd64 \
  --rollout optin
```

The generic ACP core, [bnbloc-acp](https://github.com/luckylhb90/bnbloc-acp),
is published the same way from its release binaries (its README has the
command); each member then lists their Agent Client Protocol agents in their
own `agents.json`.

An already-built package JSON (any component kind) with its detached signature:

```sh
bnbloc cores install --package acme.package.json --signature acme.package.json.sig --rollout auto
```

Other install sources: `--url <daemonURL> --name <n>` (probe a Core Protocol
daemon and sign an endpoint package) and `--manifest <file> --name <n>`.
`--rollout auto|optin|off` is applied atomically with the publish (omit it for
the gateway default, `auto`). `bnbloc cores list | uninstall <name> | enable
<name> --tenant <id>...` manage installed cores.

A sandbox package (`bnbloc.sandbox.package/v1`, see
[architecture/sandbox-protocol.md](./architecture/sandbox-protocol.md)) is
installed with `--package` too: stage its executable and each declared
`sidecar.files` artifact (`<platform>/<name>`) through the super-admin
`POST /v1/platform/artifacts` first (the gateway pins the hash it produced),
then publish the signed package. Manage it with the component routes and
`?kind=sandbox` (`cores uninstall` addresses cores only).

A notifier package (`bnbloc.notifier.package/v1`, see
[notifications.md](./notifications.md)) installs the same way; its first
install prints the component's signing secret **once** — configure it on the
notifier endpoint. Later:

```sh
bnbloc components rotate-secret corp-notify   # new secret, printed once
bnbloc components test corp-notify            # test notification to you, with the notifier's answer
```

A previewer package (`bnbloc.previewer.package/v1`, see
[architecture/previewer-components.md](./architecture/previewer-components.md))
pins one bundle archive; `previewers publish` checks the package and archive,
uploads the archive, pins its URL + sha256, signs and installs:

```sh
bnbloc previewers pack dist/site --out dist/bundle.tar      # deterministic ustar + sha256
bnbloc previewers publish --package dist/package.json --bundle dist/bundle.tar --rollout optin
```

## Publish a desktop update

```sh
bnbloc updates publish \
  --archive apps/desktop/src-tauri/target/release/bundle/macos/bnbloc.app.tar.gz \
  --signature apps/desktop/src-tauri/target/release/bundle/macos/bnbloc.app.tar.gz.sig \
  --version 1.2.3 --notes-file notes.md          # or --notes "text"; --target darwin-x86_64 for Intel
bnbloc updates status
```

Same rules as Platform → Updates in the web client
(`web/src/lib/desktopRelease.ts`, `web/src/views/updateConfigFields.ts`; Go
mirror in `cmd/bnbloc/desktop_release.go`):

1. the archive must be `bnbloc.app.tar.gz` and the `.sig` a Tauri minisign
   signature generated for that file; the version is semver;
2. the current policy channel is read (the release is published under it);
3. upload via `POST /v1/platform/artifacts` (streamed, no total timeout); the
   returned key/sha256/size must match the local file;
4. authenticated `GET /v1/artifacts/<key>` must return the same sha256 + size;
5. against freshly loaded state: refuse if the channel changed or the version
   exists on another channel; upsert `PUT /v1/platform/app-releases/<version>`
   keeping the version's other files;
6. `PUT /v1/platform/update-config`: policy kept, `enabled` turned on; a new
   version clears other targets' artifacts, the same version keeps them.

Each stage prints `[n/6]`; a failure says which stages completed (for example
"Release Hub saved, but updater configuration failed").
