# AI assist in manual entry points (2026-10-13)

Status: accepted (product owner, 2026-10-13).

Status (2026-10-13): server side built (§2–§4, the tests of §7 but the
web's). The reference is `docs/architecture/ai-assist.md`. Decided while
building:
- **The request also names the composer's channel and expert**
  (`channelId`, `expertId`): the recent messages are the channel's, and
  the expert the one picked for the message, else the room's. The room's
  skill packs are listed with the member's own.
- **Availability.** `GET /v1/assist` lists tasks only when assists run
  for the caller; a run otherwise answers 409. An organization's switch is
  `assistDisabled` in its settings (`PUT /v1/tenant/settings`).
- **An assist is no content use** (`KindSpec.Use`): turning one on in a
  room or for a member is refused, and so is a work (it never was one).
- **A JSON task** asks for `response_format: json_object`, and again
  without it when the model answers 400; a list field given as one string
  is split at commas.
- **A text task's failure** before the first piece is an HTTP 502, after
  it an `error` event.
- **The Expert builder** drafts assists too (1.3.0); a member's or an
  organization's assist of a built-in's name replaces it, nearest first.

## 1. Why

Every place a member types by hand (the composer, the publish dialog, the
Library's forms, a new room, a schedule) is a place a short sentence could
become a good draft. Members write "make a poster for the party" when the
agent would do far better with the goal, the deliverables, the
constraints and how to check the result. Other products offer an
"enhance prompt" button in the composer; we want that, and we want the
same help behind every manual form, not one feature per screen.

Agent turns are the wrong tool for this: a session of a member's agent
takes tens of seconds to start and needs a bridge online, while an assist
must answer in a few seconds, in a browser, with no desktop. So the
platform gets one small, fast model call — the **assist model** — and one
generic primitive on top of it.

## 2. The assist model

- **One model per deployment, configured by a super admin** in the
  platform console: an OpenAI-compatible chat completions base URL (a
  LiteLLM proxy, an OpenAI-compatible gateway), the model name and an API
  key.
  - The key is sealed with `BNBLOC_SECRET_STORE_KEY` (internal/sealbox,
    the settings key as additional data) and stored in platform settings;
    it is never returned, only "set". Without the secret store key the
    model cannot be configured.
  - The gateway reaches only the configured host (a guarded client, as
    endpoint components).
  - "Test" sends a one-line completion and reports the latency.
- **An organization may turn assists off** (`assistDisabled` in its
  policy), for data it does not want leaving to the model.
- **No model, no buttons.** `GET /v1/assist` answers whether assists are
  available to the caller and which tasks exist; the web hides every
  assist entry when they are not. There is no second path through
  members' agents.
- **Accounting.** Every call spends the member's cost budget, is held to
  a per-member rate limit (20 a minute), and is recorded in the audit log
  with the task, the model, the token counts and the latency — never the
  text.

## 3. Assist tasks are content

- **A new content kind, `assist`** (`bnbloc.assist.package/v1`):
  - `INSTRUCTIONS.md`: the task's system prompt.
  - `component.json` adds `output` (`text`, streamed, or `json`) and, for
    `json`, `fields`: the names the reply must hold with a short
    description each (the web knows what to fill). It also lists the
    `context` the task may receive: `room`, `artifact`, `attachments`.
- **Resolution by name**, nearest first: the member's own, then their
  organization's, then the platform's, then the built-in. An organization
  restyles "enhance prompt" by publishing its own `enhance-prompt`. The
  Library lists assists like any other kind.
- **Built-ins, first round:**
  - `enhance-prompt` (text; room, attachments): turns the composer's text
    into a clear request — goal, deliverables, constraints, how to check
    the result — in the member's language, keeping their intent and
    every concrete detail. It never invents facts; a missing fact becomes
    a `【待补充：…】`-style placeholder in the member's language. It
    uses the room's expert and skills so the request asks for what they
    do well, and returns only the rewritten request.
  - `describe-work` (json: `displayName`, `description`, `category`,
    `tags`; artifact): drafts a work's gallery entry from the deliverable
    and its recipe. Categories are the gallery's; tags follow the tag
    rule.

## 4. One API

- `POST /v1/assist/{task}`:
  - Body: `{text, roomId?, artifactId?, attachmentIds?}`. The browser only
    sends what the member typed and the ids of things it refers to.
  - The server resolves the context the task declares, after checking the
    member may read it: the room's name, expert (name, description) and
    skills (names, descriptions) and its recent messages (the last 10,
    each cut to 500 characters); the deliverable's title, type, file name
    and recipe prompt; the attachments' names and types.
  - The model sees the task's instructions as the system message, then
    one user message where everything not the member's own instruction is
    fenced (`<room>`, `<recent_messages>`, `<artifact>`, `<attachments>`,
    and the member's `<text>`), with a note that fenced text is data.
  - A `text` task streams Server-Sent Events (`delta`, then `done` with
    the usage, or `error`). A `json` task answers one object holding only
    the declared fields (strings, or a string list for `tags`); a reply
    that is not that object is a 502.
- Bounds: the text at most 8000 characters; the reply at most 2000 tokens;
  60 seconds.

## 5. The web

- **One owner**, `lib/assist.ts` (the requests, the SSE reader) and one
  `AssistButton` (the sparkle icon, a spinner while running, a stop
  button while streaming). A boundary rule keeps model requests and
  prompt text out of every other web file.
- **The composer:** a sparkle button left of the model picker, enabled
  when there is text. It replaces the text as the reply streams; "Undo"
  restores what the member wrote (also Ctrl/Cmd+Z right after). The member
  reads and edits the result before sending — nothing is sent for them.
- **The publish dialog:** "Fill with AI" drafts the name, description,
  category and tags from the deliverable. The fields fill in, the member
  edits them, and nothing is published until they press Publish.
- **The platform console:** an "Assist model" card (base URL, model, key
  write-only, Test). **The organization page:** an "AI assist" switch.

## 6. The second round (accepted 2026-10-13)

The same primitive behind the remaining manual forms, plus an
organization's own model. Each entry is a built-in task and a button; the
platform grows only the field shapes and two contexts below.

- **Richer reply fields.** A JSON task's field has a `type`: `text` (a
  string, the default), `list` (strings) or `items` (a list of objects
  whose own fields, `item`, are strings). This replaces the `list` flag;
  pre-launch, no compatibility. The server holds a reply to these shapes
  (unknown keys dropped, items without any declared field dropped, at
  most 20 items); the content validator still owns what is saved.
- **New contexts**, resolved by the server like the others:
  - `library`: the experts and skill packs the member can use (id, name,
    display name, description; at most 40 of each, the member's own and
    their rooms' first), so a task can recommend real components by name.
  - `clock`: the current time in the member's timezone. The request
    gains `timezone` (an IANA name the browser reports; UTC when absent or
    unknown).
- **Library: draft from a sentence.** The new/edit form of an expert, a
  skill pack and a prompt pack gets "Draft with AI": the member writes one
  sentence (or uses what the form already holds) and the form fills in.
  Nothing is saved until they press Save. "Create with AI" (the workshop
  conversation, which can write scripts and test them) stays for deeper
  work.
  - `draft-expert`: display name, description, instructions, welcome,
    quick prompts (`items`: title, prompt), tags.
  - `draft-skill-pack`: display name, description, skills (`items`: name,
    description, body), tags.
  - `draft-prompt-pack`: display name, description, prompts (`items`:
    title, prompt), tags.
- **New room from a goal.** The new-room dialog gets "Plan with AI": the
  member describes what the room is for, and `plan-room` (`library`)
  proposes the room id, name, description, an expert and skill packs
  (by name, from the library) and a first message. The member edits the
  proposal; on Create the room is made, the expert and skills are turned
  on (only those the member may use; an unknown name is dropped), and the
  first message waits in the composer, not sent.
- **Schedules in plain words.** The schedule form gets "Describe it":
  `draft-schedule` (`clock`) turns "every weekday at 9:30 remind the team
  of the standup" into the message text and the recurrence (`kind`,
  `time`, `days`, `cron`, `at` as a local `YYYY-MM-DDTHH:MM`). The form
  shows the result and the next run time; the member saves it.
- **An organization's own model.** An org admin may set the
  organization's model (base URL, model, key, sealed per organization),
  which replaces the platform's for its members. Its host must be one the
  super admin allowed (`orgHosts` on the platform's model; none by
  default), so an organization cannot point the gateway at an arbitrary
  address. The organization's switch still turns assists off entirely.
  Test works the same.

## 7. Tests

Second round: the field shapes (items held, extras dropped); the library
and clock contexts (only what the member may use; the timezone); each new
built-in's golden and budget; the organization's model (sealed, host
allowlist, replaces the platform's, the switch still wins); web: each
form's fill, the new room's apply (unknown names dropped, the draft
waits), the schedule's parse.

First round:

- The settings: the key is sealed and never returned; no secret store key
  refuses; only super admins configure it.
- The client: a streamed reply is relayed, a JSON reply is held to its
  fields, the host guard holds, a timeout and a model error are reported.
- The API: an organization that turned assists off and a missing model
  answer unavailable; a room or deliverable the member cannot read is
  refused; untrusted text is fenced; the audit row holds no text; the
  rate limit.
- The kind: `assist` validation; resolution nearest first.
- Built-in instructions: goldens and a token budget.
- Web: the SSE reader, the composer's replace and undo, the publish
  dialog's fill, hidden when unavailable.
