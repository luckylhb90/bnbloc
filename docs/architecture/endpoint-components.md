# Endpoint components: the credential and the settings ask

An endpoint component runs beside the gateway, as a service the operator
deploys (`runtime: "endpoint"`): a notifier (`bnbloc.notifier.package/v1`,
[notifications.md](../notifications.md)) or an auth provider
(`bnbloc.auth-provider.package/v1`). bnbloc never starts it, so nothing can
be delivered to it at launch the way a plugin or a stdio MCP tool gets its
settings. Instead it holds one **credential** and **asks** for its settings
(docs/prd/2026-10-19-component-settings.md §2.3, slice 3).

## The credential

- **One per installed component** (`internal/componentcred`, the one owner):
  32 random bytes, `whsec_<hex>`, generated by the gateway when the
  component is first installed and answered **once** (the install
  response's `secret`; the console shows it with a copy button, the CLI
  prints it). An upgrade keeps it; an upgrade of a component installed
  before it held one creates it then (shown once).
- **Sealed at rest**: platform settings key
  `component.credential/<kind>/<name>`, sealed with `BNBLOC_SECRET_STORE_KEY`
  (`internal/sealbox`, bound to its key, so a row moved to another key does
  not open). The gateway creates, rotates and verifies it; realtime opens a
  notifier's to sign deliveries, so both need the key. Without the key on
  the gateway a notifier or auth provider install is refused (409).
- **Rotate**: `POST /v1/platform/components/{name}/secret/rotate?kind=<kind>`
  (super admin; `bnbloc components rotate-secret <name> --kind <kind>`;
  "Rotate secret" on the component's card) answers a new one once and
  audits `rotate-secret`. The old one stops verifying at once: put the new
  one on the component (a notifier's receiver takes a comma list during
  the change).
- **Deleted** with the component (uninstall).
- **Before sealing.** A notifier's signing secret was stored in clear under
  `notify.secret/<name>`. It is still read (gateway and realtime, with or
  without the key) until the first rotation or the uninstall removes it;
  nothing writes it. Remove this read once no deployment holds such a row.

## Signed calls

A component's call to the gateway names it in `X-Bnbloc-Component` and
signs with its credential in `X-Bnbloc-Signature`, the scheme bnbloc's
deliveries use: `t=<unix seconds>,v1=<hex(HMAC-SHA256(credential, t + "." +
signed))>`, accepted within 5 minutes of the gateway's clock (either side),
compared in constant time. `signed` is the raw body of a POST, and
`"<METHOD> <path>"` of a GET (no query): `GET /v1/component-settings`.
`verifyComponentCall` (services/gateway/component_credential.go) is the one
check of every signed route (`TestComponentCallSingleOwner`).

| Route | `X-Bnbloc-Component` | Signed |
| --- | --- | --- |
| `POST /v1/notifier/replies`, `/reply-refs`, `/group-binds` | the notifier's name | the body |
| `GET /v1/component-settings` | `<kind>/<name>` (`notifier/corp-notify`, `auth-provider/corp-sso`) | `GET /v1/component-settings` |

Refusals: `401` no or malformed header, a kind that holds no credential,
no credential stored, a bad or stale signature (another component's name
signed with this one's credential fails here); `403` not installed.

## The settings ask

`GET /v1/component-settings` answers the calling component's values
(`wire.EndpointComponentSettings`):

```json
{
  "kind": "auth-provider", "name": "corp-sso",
  "version": "9f2c…",
  "platform": { "metadataUrl": "https://idp.example.com/metadata", "spKey": "-----BEGIN PRIVATE KEY-----…" },
  "orgs": { "acme": { "groupAttribute": "memberOf" } },
  "missing": { "platform": [], "orgs": { "acme": [] } }
}
```

- `platform`: the stored platform values of the settings it declares,
  **secrets included** (the component needs them). A setting with no stored
  value is absent: the component applies its own default (the declaration's
  `default` is for the form), so a value the component reads elsewhere
  (during a migration, its own environment) is not overridden by a default.
- `orgs`: each organization's stored organization values, for the
  organizations the install serves (its rollout and tenant scope,
  `extpipe.TenantDistribution`) that have stored any.
- `missing`: the required settings without a value, per scope.
- `version`: a hash of the rest. Poll, and apply an answer only when its
  version changed.
- `409` when the gateway has no secret store key; the answer is never
  logged and reads are not audited.

A component **asks at start and then every minute or so (with jitter)**,
keeps the last good answer when an ask fails, and applies a changed one
without a restart (rebuilding what depends on it, keeping the old state
when the new values do not work, and saying why in its log). A saved value
reaches it on its next ask; the settings form says so ("The component reads
these values from the gateway itself").

## Declaring settings

An endpoint component declares `settings` like any component
(`core/pkgmeta/settings.go`), with two rules of its own
(`pkgmeta.AsksForSettings`): scope `platform` or `org` only (nothing of a
member's reaches a service beside the gateway), and no `deliver` (it asks).
No `settingsPage`: the one form renders the declaration. Its platform
settings are set in Platform console → Components → the component →
Settings; organization settings in Organization → Component settings,
which lists components of every kind (`GET /v1/tenant/component-settings`),
since an endpoint component is in no member's catalog.

What stays in the component's deployment environment is only what it needs
before it can ask: where it listens, the gateway's address, its credential,
and whatever loads them (a secret manager reference).
